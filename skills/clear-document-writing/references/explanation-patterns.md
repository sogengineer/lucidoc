# 伝わる説明の型（Step 4・5 の実行資料）

SKILL.md の Step 4（文章の構成）と Step 5（文を書く）で、パラグラフや章の**中身の組み立て方**として使う型をまとめる。文単位の推敲は `sentence-refinement.md`、結論を先に書くこと、図表にすること、まとまりに分けることは、そちらと SKILL.md 本文にあるので、ここでは繰り返さない。

型は4つのまとまりに分かれる。文書に関係するまとまりだけ使えばよい。

| まとまり | 読み手の問い | 型 |
|---|---|---|
| A. 本題に乗せる | 何の話か。自分に分かる話か | 前提を先に補う／具体的な値で示す／用語を初出で言い換える |
| B. 違いを見せる | 何が変わり、何が変わらないか | 前と後を並べる／変わること・変わらないことを分ける／太字は読み落とすと困る差だけ |
| C. 判断を受け渡す | なぜそう決めたか。自分は何を決めればいいか | 経緯と根拠を残す／判断してほしい点に番号と自分の考えを添える |
| D. 裏付けを置く | 本当にそうなるのか | 確かめた結果を「結論 → 条件 → 結果 → 証跡」の順に並べる／流れを止める付帯情報は畳む |

例はすべて、架空の題材「定期便サービスで、解約日より後の配送予約を受け付けていた不具合を直す」で示す。

## A. 本題に乗せる

### 前提を本題の前に補う

**読み手が知らない仕組み・用語は、本題に入る前に最小限だけ説明する。** 本題の途中で前提が出てくると、読み手はそこで止まって読み返す。冒頭に「そもそも何の話か」を置き、結論の1〜2文のすぐ後に、本題を読むのに要る前提を入れ子の箇条書きで足す。前提は本題を理解するのに要る分だけにする。網羅すると本題が埋もれる。

```
改善前:
解約日より後の配送予約を、登録時に断るようにします。一括登録の判定もあわせて変えます。

改善後:
解約日より後の配送予約を、登録時に断るようにします。解約日の当日の配送は、今までどおり登録できます。

- 定期便は、会員が選んだ日に商品を届けるサービスです。
  - 配送予約の登録は、管理画面で1件ずつ登録する「個別登録」と、CSV でまとめて登録する「一括登録」の2通りです。
```

### 具体的な値で示す

**問題・ルールは、抽象的な説明に加えて、実際の値を入れた例で示す。** 「解約後の予約を受け付けてしまう」だけでは、どの日付なら起きるのか読み手が頭の中で組み立てる必要がある。値の入った例があれば一読で分かる。

- 起きていることは「例: 解約日が 3/20 の会員に、3/21 着の予約を登録できる。3/21 に実際に発送される」のように書く。
- 判定のルールは「解約日 < 配送予定日 なら断る」のように1行の式で書く。文章だけだと「以前」「以降」「より前」の境界が読み手ごとに割れる。
- 境界の扱いは明示する。前日・当日・翌日のように境界の前後を並べ、どれが通りどれが断られるかを書く。

### 用語は初出で言い換える

**読み手が知らないかもしれない用語は、最初に出てきた箇所で括弧書きの短い言い換えを添える。** 用語集に分けると読み手は行き来する必要がある。初出の括弧書きなら流れを止めない。2回目以降は言い換えず、同じ用語で通す（途中で呼び名を変えると、別の物だと誤解される）。

| 改善前 | 改善後 |
|---|---|
| 「API 側で配送基盤を呼ぶ前に弾く」 | 「配送基盤（倉庫に出荷を指示する外部のシステム）を呼ぶ前に断る」 |
| 「個別登録」「単発登録」「1件登録」が混在 | 「個別登録」で統一 |

## B. 違いを見せる

### 前と後を並べる

**変更や比較は、前と後を左右（または上下）に並べ、同じ形式で描く。** 別々の段落に書くと、読み手は差分を自分で探す必要がある。同じ形の図・表を並べれば、違う箇所だけが目に入る。複数のアクターが関わるならシーケンス図を2つ並べる（図の選び方は `sentence-refinement.md`「図表で表す」）。

Markdown の表でセルに図を入れられない環境（GitHub など）では、HTML の `<table>` で2列にし、各セルの中に図を置く。

### 変わること・変わらないことを分ける

**影響範囲は「変わること」と「変わらないこと」を分けて書く。** 読み手が気にするのは「自分の関わる部分に影響があるか」。変わることだけ書くと、書かれていない部分が「変わらない」のか「書き忘れ」なのか区別できない。変わらないことを明記すると、読み手は安心して読み飛ばせる。

```
- 変わること
  - 個別登録: 配送予定日が解約日より後のとき、登録できなくなる
  - 一括登録: 解約日の当日の行が、エラーから登録できるようになる
- 変わらないこと
  - 解約日が決まっていない会員の予約
  - 一括登録で、解約日より後の行はエラー（今までどおり）
```

### 太字は読み落とすと困る差だけ

**太字は、読み落とすと読み手が判断を誤る箇所だけに使う。** 例えば、意図的に既存の挙動から変えた点や、確認結果のうち「断られた」行などに付ける。多用すると、どれも目立たなくなる。

## C. 判断を受け渡す

### 経緯と根拠を残す

**「なぜこうしたか」は、根拠の一次情報を示して書く。** 「仕様なので」だけでは、読み手は判断の正しさを確かめられない。

- 根拠になった回答・決定は、要点を引用して載せる。要点を言い換えて載せると、元の意図からずれることがある。
- 方針が途中で変わったら、「当初は X にしていた → Y と決まった → Z に変えた」の順で書く。最終形だけ書くと、古い前提を知っている読み手が混乱する。
- 決まったことは「何を決めたか・理由」を対にして、決めた日付と並べる。理由が無い決定は、あとで覆してよいのかが読み手に分からない。

### 判断してほしい点に番号と自分の考えを添える

**読み手に判断を求める箇所は、番号を振って分け、各項目に「自分はこう考える＋理由」を添える。** 問いだけを投げると、読み手は前提から考え直す必要がある。書き手の考えがあれば、読み手は賛否を言うだけで済む。

- 重い判断と軽い確認は分ける。「小さめの確認です」のように区切りを入れると、読み手は時間をかける箇所を選べる。
- 書き手に考えが無いとき（選択肢を決めかねているとき）は、その旨と、何が決まれば進められるかを書く。

```
改善前:
- 判定を登録処理の中に置きましたが問題ないでしょうか。

改善後:
1. 判定を登録処理の中に置くこと
   - 私はこれでよいと考えます。どの画面から登録しても必ず通るためです。
   - なお、一括編集は登録処理を通らないため、この判定は効きません（下の 3）。
```

## D. 裏付けを置く

### 確かめた結果は「結論 → 条件 → 結果 → 証跡」の順に並べる

**動作確認・調査の結果は、何が確かめられたかを1文で先に書き、そのあとに条件・結果・証跡を続ける。** 読み手の多くは結論で読むのをやめる。疑問を持った読み手だけが、条件と証跡まで読み進める。

| 順 | 書くこと | 例 |
|---|---|---|
| 1. 結論 | 何が確かめられたか | 解約日の当日は登録でき、翌日は断られることを確かめた |
| 2. 条件 | 用意したデータ・環境 | 解約日が 3/20 の会員、実行日 3/13 |
| 3. 結果 | 境界ごとの結果 | 3/19: 登録される / 3/20: 登録される / **3/21: 断られる** |
| 4. 証跡 | 画面・ログ・応答 | スクリーンショット、API の応答（折りたたみ） |

確かめられなかったことは、理由と代わりに確かめた手段を添えて書く（例:「当日の即時発送は外部システムが要るため画面では確かめていない。自動テストで確かめた」）。黙って省くと、読み手は確かめたものと受け取る。

### 流れを止める付帯情報は畳む

**本筋の理解に要らないが、残す必要のある情報（生ログ・テンプレートの必須項目・変更ファイル一覧）は、折りたたみ（`<details>`）や末尾の章に送る。** 本文に混ぜると、流し読みする読み手が要点を拾えなくなる。畳むときは、見出し（`<summary>`）に中身が分かる名前を付ける（「詳細」ではなく「API の応答と DB（修正後）」）。
