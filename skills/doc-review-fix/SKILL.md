## Instructions

### そもそもこのスキルは何か

書き上げたドキュメント1本を、別の目でレビューして、その場で直すスキルです。**レビュー → 分類 → 修正 → 見直し → 結果の書き出し** を1回だけ行います。直したあと問題が無くなるまで繰り返すのは [[doc-review-fix-loop]] の仕事です。

この手順書で使う言葉:

- **白箱レビュー**: 決まった基準（ルーブリック）に照らして採点するレビュー。規則違反を見つける
- **黒箱レビュー**: 想定する読み手になりきり、初見で読んで目的を果たせるかを確かめるレビュー。読み手が実際に困る点を見つける
- **事実照合**: 文書の内容を元資料（コード・仕様・議事録など）と突き合わせ、誤りを見つけるレビュー
- **深刻度**: critical＝読み手が目的を果たせない、または誤情報がある／major＝果たせるが手間が大きく増える／minor＝読みやすさの改善余地
- **要確認**: 元資料に無く、書き手が埋められない情報。作らずに「要確認」と書いて残す
- **収束（CONVERGED）**: 直すべき critical・major が残っていない状態

### なぜこの進め方か

- **書いた本人は、自分の曖昧さや抜けに気づけない。** だからレビューは、新しく起動したサブエージェントにやらせる。
- **白箱と黒箱では、見つかるものが違う。** 規則は守っていても読み手が困る文書があり、その逆もある。だから両方かける。
- **無い情報を作って埋めると、誤情報になる。** 読み手が「足りない」と言っても作らず、「要確認」と書いて人に確かめてもらう。
- 判断の基準は「読み手が効率よく目的を達成できるか」。きれいに書けたかでは評価しない。

### 入力

| 入力 | 説明 | 取り方 |
|------|------|--------|
| 対象ファイル | レビューするドキュメント | 引数、または直近に作成した成果物。**特定できない場合は推測せず、ユーザーに確認する** |
| 読み手像 | 「誰に・何を・何のために」 | 引数、またはドキュメント冒頭・タイトルから読み取る。取れなければ本文から推定し「読み手像（推定）」と書く |
| 元資料 | 文書の出典（コード・議事録・仕様の原典） | 引数、または本文のリンクから。**あれば C（事実照合）が必須** |
| 結果ファイルパス | 結果の書き出し先 | 引数。既定は作業用の一時フォルダの `doc-review-fix-result-<対象ファイル名>.md` |

### 進み具合の表示（必須）

数分かかるので黙らない。着手時・レビュー完了時（critical/major/minor の件数）・修正完了時（自動修正／情報補充／要確認の件数）・完了時（対応サマリと収束判定）に短文で出す。

### Phase 1: レビュー（サブエージェントを並列に起動）

| 系統 | 何を見るか | 人数 | モデル |
|------|-----------|------|--------|
| A. 白箱 | 書き方の原則を守っているか（下のルーブリック） | 1名 | sonnet |
| B. 黒箱 | 初見の読み手が目的を達成できるか | 2〜3名 | sonnet |
| C. 事実照合 | 名前・値・条件・順序が元資料と一致するか。**元資料があるときだけ・必須** | 1名 | opus |

モデルは Agent ツールの `model` で指定する。指定できない環境では、A・B は軽いモデル、C は最上位のモデルを使う。それもできなければ既定のモデルで進め、結果ファイルの「レビュー構成」に書く。

**全レビュアーに共通の返し方**:

```
- 観点: <ルーブリック#番号 または Q1-Q4>
  深刻度: critical | major | minor
  箇所: <見出し名とおおよその位置>
  引用: <問題の箇所を本文からそのまま引用。書かれていないことの指摘なら、その情報があるべき箇所の直前の文を引用>
  指摘: <何が問題か>
  提案: <どう直すか。情報が無くて直せないなら「要情報: <何が足りないか>」>
```

- **引用の無い指摘は、集約するときに捨てる。**
- critical と major は全件返させる。minor は重要な順に最大5件まで。

#### A. 白箱レビュアーへの依頼文

```
あなたはドキュメントの構成レビュアーです。以下のドキュメントを読み、下のルーブリック
各項目を「合格 / 要修正」で採点してください。要修正には深刻度（critical/major/minor）と
箇所・引用・提案を、指定フォーマットで挙げてください。ドキュメント外の情報は参照しません。
合格・要修正で迷った項目は要修正とし、引用を添えて理由を書いてください。
本文中の「要確認」の印そのもの（元資料に無い情報を作らずに残した印）は指摘しないでください。

## ドキュメント
（Read で対象ファイルを読む。パス: <対象ファイル>）

## 読み手像
<誰に・何を・何のために>

## ルーブリック
1. 目的の明示: 誰に・何のためかが冒頭から読み取れるか
2. 1読み手1目的: 複数の読み手が混在して焦点がぼけていないか
3. Why/What/How: How（操作）偏重で Why・What が欠落していないか
4. 流し読み成立: 見出しだけで全体のあらましが掴めるか
5. 見出しの具体性: 「詳細」「その他」「〜とは」止まりで主張のない見出しがないか
6. 中心文の位置: 各段落の先頭に結論（中心文）があるか／1段落1主張か
7. 文の明確さ: 「適宜」「なるべく」「等」、一文多義、回りくどい否定形がないか
8. 読み手視点: 仕組みの説明に終始せず、得るもの・すべき操作が書かれているか
9. 図表の活用: 複数アクターの流れを文章でだらだら書いていないか／逆に図の作りすぎがないか
10. 引き算: 読み手の目的に効かない情報が混ざっていないか
11. 形式: frontmatter・リンク・体裁が崩れていないか

## 出力フォーマット
（上記の指摘フォーマットで、要修正の項目だけ列挙）
```

#### B. 黒箱レビュアー（読み手）への依頼文

2〜3名を、それぞれ別に起動する。Q1 は読み手像を見せる前に答えさせる。

```
以下のドキュメントを初見で読むレビューです。上から順に回答してください。
ドキュメントの外にある情報は参照せず、書かれていることだけから判断してください。
本文中の「要確認」の印そのもの（元資料に無い情報を作らずに残した印）は指摘しないでください。

## ドキュメント
（Read で対象ファイルを読む。パス: <対象ファイル>）

## Step A（ドキュメント本文のみから回答。下の「読み手プロフィール」はまだ参照しない）
Q1: このドキュメントは誰の・何のためのものだと読み取れたか？

## 読み手プロフィール（Step B で使う）
あなたは次の読み手です:「<読み手像>」。

## Step B（読み手プロフィールの立場で回答。各1-2文）
Q2: 読み終えて、あなた（読み手）は目的を達成できるか？「できる」なら、達成に使った箇所を本文から引用して挙げる（挙げられないなら「できない」とする）。できないなら何が足りないか？
Q3: 曖昧・多義的で、解釈が割れた箇所はどこか？
Q4: 読み飛ばしても支障ない（不要な）情報はあったか？

## 回答後、気づいた問題を指定フォーマットで挙げてください
（Q2 未達は critical、Q3 は major〜minor、Q4 は minor。Q1 は回答のみでよい）
```

Q1 の答えが読み手像と食い違っていたら、集約するときに critical とする（判定は集約する側が行う）。

#### うまく起動できなかったとき

- 黒箱の有効な回答が2名未満なら、1回だけ起動し直す。それでも足りなければ続けてよいが、「レビュー構成」に「黒箱: M名（N名中、失敗により縮退）」と書く。
- サブエージェントを起動できない環境では、A は自分で採点し、B は自分が読み手になりきって Q1〜Q4 に答える。「読み手レビューは自己レビューで実施」と書く。レビューを黙って飛ばさない。

### Phase 2: 分類（main session）

重複（同じ箇所・同じ趣旨）をまとめ、各指摘を3つに分ける。

- まとめた指摘の深刻度がレビュアーで割れたら、高い方を採る。
- 1つの指摘の一部だけ直せた（残りは情報が無い）ときは、「要確認で残置」に数える。
- 情報が無くて直せない minor も「要確認で残置」に数える。

| 分類 | 条件 | 対応 |
|------|------|------|
| 自動修正 | 書き換え・並べ替え・図表化・削除だけで直る | Phase 3 で直す |
| 情報補充 | critical または major で、足りない情報が**元資料・文脈・既存資料にある** | Phase 3 で本文に補う |
| 捏造リスク | critical または major で、足りない情報が**どこにも無い** | **作らない**。本文に「要確認」と書き、何が足りないかを結果ファイルに残す。対応サマリでは「要確認で残置」に数える |

**情報補充と捏造リスクの線引き**:

- 情報補充にしてよいのは、足りない情報が元資料・与えられた文脈・既存資料に**はっきり書かれている**ときだけ。文書の別の節にある内容の移動・言い換えも含む。
- システム固有の値・コマンド・名前・パス・時間などで出典に無いものは、もっともらしくても捏造リスクにする。
- どの環境でも成り立つ一般論の理由（例: メンテナンスモードは書き込みを止める）は補ってよい。ただし、この文書の環境の挙動として断定しない。迷ったら要確認にする。
- 文書の中で記述が食い違い、出典でどちらが正しいか決められないときは、片方に揃えない。両方を残して要確認にする。
- 出典に無いメタ情報（担当者・作成日など）は埋めない。frontmatter を足すなら、不明な値は `要確認` と書く。

---

### Phase 3: 修正（main session）

「自動修正」と「情報補充」を対象ファイルに適用し、どこをどう直したかを記録する。直し方は [[clear-document-writing]] の各 Step に従う（見出しは Step 3、段落は Step 4、文・図表は Step 5）。

**書き換えた文は、sonnet のサブエージェントに yomiyasu スキルで推敲させる。**

- 対象は、このパスで変えた箇所の文だけ（変えていない箇所まで書き換えると、次のレビューで新しい指摘を生む）。
- 渡すもの: 対象ファイルのパス、推敲する箇所、読み手像。推敲稿は別ファイルに出させる。
- 呼び出す名前: プラグインで導入した Claude Code では `yomiyasu:yomiyasu`、それ以外は `yomiyasu`。
- 推敲稿を受け取ったら、事実・数値・条件・固有名・「要確認」の印が変わっていないか確かめる。変わっていたらその箇所は戻す。確かめてから対象ファイルに書き戻す。
- yomiyasu の規則とぶつかったら、このスキルを優先する（「要確認」の印は残す）。
- サブエージェントを起動できなければ自分で yomiyasu を呼ぶ。yomiyasu が使えなければ [[clear-document-writing]] の `references/sentence-refinement.md` の基準で直し、「yomiyasu 未使用（理由）」と書く。

---

### Phase 4: 見直しと収束判定

直した箇所とその前後だけを読み直し、新しい曖昧さや食い違いを生んでいないか確かめる（全体の読み直しはループの次の周が行う）。

件数は、修正したあとに**まだ残っている数**で数える。

| 条件 | 判定 |
|------|------|
| 残る critical = 0、残る major = 0、読み手全員が「目的を達成できる」 | **CONVERGED** |
| 残る critical・major が「要確認で残置」だけ | **CONVERGED** |
| それ以外 | **NOT_CONVERGED** |

Q2 の数え方:

- 「条件付きで達成できる」は、その条件で判断する。足りないものが要確認で残した不足だけなら「達成できる」に数える。
- 「できない」でも、理由が要確認で残した不足だけなら、未達に数えない。

単体で実行して修正したうえで CONVERGED としたときは、「1パス判定・修正後の全体の再確認は未実施」と書き添える。

---

### Phase 5: 結果の書き出し

ユーザーに表示し、同じ内容を結果ファイルにも書く。`対応サマリ` 表と `収束判定` 節は**必ず**入れる（無いとループ側が NOT_CONVERGED と扱う）。

```
# doc-review-fix 結果: <ファイル名>

## 対応サマリ
| 深刻度   | 検出 | 修正済み | 要確認で残置 |
| -------- | ---- | -------- | ------------ |
| critical | 2    | 1        | 1            |
| major    | 3    | 3        | 0            |
| minor    | 4    | 4        | 0            |

## 主な修正
- <観点/箇所>: <どう直したか>

## 要確認で残した不足（作らずに残したもの）
- <何が足りないか / 誰に確認すべきか>

## レビュー構成
- 白箱: 1 / 黒箱: N（起動できなかった場合はその旨）
- yomiyasu: 使用 / 未使用（理由）
- モデル: 指定どおり / 指定できず（使ったモデルと理由）

## 収束判定
CONVERGED | NOT_CONVERGED
```

### 補足

- **C だけ最上位のモデルにする理由**: A・B は文書の外を見ないので、誤情報を見つけられるのは C だけ。誤情報は最も重い問題なので、C に一番強いモデルを使う。
- **引用を必須にする理由**: 根拠のない指摘と、問題を見つけながら「大したことはない」と見逃す甘い評価の両方を減らすため。
- **minor を5件までにする理由**: レビュアーの返答はすべて main session の文脈に入る。細かい指摘で文脈を埋めないため。
- **1パス判定の限界**: Phase 4 は直した本人の見直しなので、甘くなりうる。修正後の新しい目での確認は [[doc-review-fix-loop]] が行い、この判定を上書きする。
- 判断の基準「読み手が効率よく目的を達成できるか」は、ISO 9241-11 の有効性・効率に対応する。
